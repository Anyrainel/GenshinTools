# Worker Backup API Design

Last updated: 2026-05-01.

## Goal

Design a Workers-first, domain-agnostic backup API for automatic backup, restore, and multi-device conflict handling.

The Worker should behave like an authenticated key-value backup service:

- key: opaque `partitionKey`
- value: immutable compressed backup object
- current pointer: per-partition `head`
- concurrency token: per-partition `rev`

The Worker should not know whether a partition is game profile data, builds, teams, tiers, or future domains. Domain transforms stay in `src/cloud/adapters/**`.

## Current Naming

Use these terms:

| Term | Meaning |
| --- | --- |
| `partitionKey` | Opaque logical backup key, for example `builds/all` or `profile.artifacts/0`. |
| `head` | The current published backup object pointer for one partition key. |
| `objectId` | Server-generated id of one immutable stored backup object. Used for download. |
| `rev` | Server-generated opaque concurrency token for one partition head. |
| `headSetRev` | Server-generated opaque token for the authenticated user's full current head set. Used for cheap no-change checks. |
| `commit` | Atomic publish operation for changed objects and/or deletes. |
| `idempotencyKey` | Client-generated retry key for one commit request. |
| `commitObjectKey` | Client-generated key for one object inside a commit request. |
| `writeMode` | Per-entry server-enforced write policy: `ifMatch`, `ifAbsent`, or `overwrite`. |
| `deviceId` | Stable public id generated by the browser for sync diagnostics. Not authentication. |
| `deviceLabel` | Optional automatically inferred display label for conflict UI. |

Avoid external API terms like `namespace`, `shard`, `stagedObject`, `batch`, `uploadId`, or `clientBatchId`.

## Auth Assumptions

Auth provider choice should not change the backup API contract.

Required server-side auth boundary:

- Every backup endpoint resolves an authenticated app `userId`.
- The Worker checks `cloud_sync` entitlement before reads or writes.
- The client sends a device id generated by `useCloudSyncMetadataStore`. This id is not trusted for auth; it is only for diagnostics and conflict display.
- Provider details, whether Azure, GitHub, Google, Gitee, WeChat, or another provider, are hidden behind `requireUser(request, env)`.

Auth is not a blocker for the API design. It becomes a blocker before public deployment of read/write endpoints, because the Worker must reliably map a request to one app user and enforce that user's object ownership.

Current implementation status:

- Public auth is not wired yet.
- The Worker route is intentionally dev-gated with `Authorization: Bearer <BACKUP_DEV_AUTH_SECRET>` and `x-backup-dev-user-id`.
- Without `BACKUP_DB`, `BACKUP_BUCKET`, and `BACKUP_DEV_AUTH_SECRET`, `/api/backup/v1/*` returns an unavailable JSON error and does not read or write anything.

Recommended auth interface:

```ts
type AuthenticatedUser = {
  userId: string;
  sessionId: string;
  entitlements: Set<"cloud_sync" | string>;
};

async function requireUser(request: Request, env: Env): Promise<AuthenticatedUser>;
```

If Azure works for both China and US users, use it to establish identity, then issue or validate a first-party app session. The backup API should not store Azure access tokens or depend on Azure-specific claims outside the auth adapter.

## Device Identity

`deviceId` is generated client-side once per browser profile/install and persisted in `useCloudSyncMetadataStore`.

Recommended generation:

```ts
crypto.randomUUID()
```

Fallback can be random enough for display diagnostics, but this is not an auth secret and not a trusted authorization input.

`deviceLabel` is optional user-facing text computed automatically when practical. Users do not provide labels.

It can be:

- inferred from user agent, such as `Chrome on Windows`
- inferred from a platform hint if the browser exposes one
- omitted

If reliable automatic labeling is hard or too privacy-sensitive, omit the label entirely. The backup feature must not depend on device labels.

The server stores device rows per authenticated user:

```sql
CREATE TABLE backup_devices (
  id TEXT PRIMARY KEY,
  user_id TEXT NOT NULL REFERENCES users(id) ON DELETE CASCADE,
  device_id TEXT NOT NULL,
  label TEXT,
  created_at INTEGER NOT NULL,
  last_seen_at INTEGER NOT NULL,
  last_backup_at INTEGER,
  UNIQUE(user_id, device_id)
);
```

## Schema Version

`schemaVersion` on a backup object is the payload schema version for that partition's cloud payload.

It is not the API version.

- API version is in the route: `/api/backup/v1/*`.
- Payload schema version is inside object metadata and the object envelope.

Example:

```ts
{
  partitionKey: "builds/all",
  schemaVersion: 1,
  contentHash: "sha256:..."
}
```

The Worker only checks that the schema version is allowed for backup storage. The frontend owns payload migrations during restore.

The payload content may also contain its own schema version if that is convenient for adapter validation or migrations. The top-level DB/header `schemaVersion` exists so the Worker can index, filter, debug, and report storage analytics without decompressing or parsing backup bodies.

## Storage Model

Use D1 for metadata and R2 for compressed backup bodies.

V1 should minimize D1 write volume:

- one aggregate row per user for cheap no-change checks
- one current-head row per `userId + partitionKey`
- one short-lived commit idempotency row per write request
- optional device rows for diagnostics

Do not store one row per temporary upload object in V1. The commit request carries the changed object bytes directly, and the Worker writes those bytes to R2 before publishing the D1 head updates.

Minimum D1 tables:

```sql
CREATE TABLE backup_user_state (
  user_id TEXT PRIMARY KEY REFERENCES users(id) ON DELETE CASCADE,
  head_set_rev TEXT NOT NULL,
  updated_at INTEGER NOT NULL,
  key_count INTEGER NOT NULL DEFAULT 0,
  total_compressed_bytes INTEGER NOT NULL DEFAULT 0
);

CREATE TABLE backup_heads (
  user_id TEXT NOT NULL REFERENCES users(id) ON DELETE CASCADE,
  partition_key TEXT NOT NULL,
  object_id TEXT NOT NULL,
  rev TEXT NOT NULL,
  schema_version INTEGER NOT NULL,
  content_hash TEXT NOT NULL,
  compressed_hash TEXT NOT NULL,
  compressed_bytes INTEGER NOT NULL,
  updated_at INTEGER NOT NULL,
  source_device_row_id TEXT REFERENCES backup_devices(id) ON DELETE SET NULL,
  soft_deleted_at INTEGER,
  PRIMARY KEY(user_id, partition_key)
);

CREATE TABLE backup_commits (
  id TEXT PRIMARY KEY,
  user_id TEXT NOT NULL REFERENCES users(id) ON DELETE CASCADE,
  idempotency_key TEXT NOT NULL,
  device_row_id TEXT REFERENCES backup_devices(id) ON DELETE SET NULL,
  result_json TEXT NOT NULL,
  created_at INTEGER NOT NULL,
  expires_at INTEGER NOT NULL,
  UNIQUE(user_id, idempotency_key)
);
```

`backup_commits` is not a staging table. It is a retry ledger. If a client loses the response after a successful write, it can retry the same `idempotencyKey` and receive the original result instead of publishing a second version or seeing an ambiguous conflict.

Optional object history table:

```sql
CREATE TABLE backup_objects (
  id TEXT PRIMARY KEY,
  user_id TEXT NOT NULL REFERENCES users(id) ON DELETE CASCADE,
  partition_key TEXT NOT NULL,
  rev TEXT NOT NULL,
  commit_id TEXT NOT NULL,
  schema_version INTEGER NOT NULL,
  r2_key TEXT NOT NULL,
  content_hash TEXT NOT NULL,
  compressed_hash TEXT NOT NULL,
  logical_bytes INTEGER NOT NULL,
  compressed_bytes INTEGER NOT NULL,
  source_device_row_id TEXT REFERENCES backup_devices(id) ON DELETE SET NULL,
  created_at INTEGER NOT NULL,
  superseded_at INTEGER,
  deleted_at INTEGER,
  UNIQUE(user_id, partition_key, rev)
);
```

If `backup_objects` is kept, it must be retention-capped from the start. V1 can also skip this table and treat `backup_heads.object_id` plus R2 object metadata as the durable current object index.

If V1 skips `backup_objects`, `/objects` should authorize downloads by current `backup_heads` rows only. A stale object id that is no longer a current head can be rejected and the client can refresh `/head`.

R2 key shape:

```text
users/{userId}/backup/objects/{objectId}.json.gz
```

All path segments must be server-generated or server-encoded.

## API Overview

Use this versioned prefix:

```text
/api/backup/v1/*
```

Endpoints:

```text
GET  /api/backup/v1/head
POST /api/backup/v1/commits
POST /api/backup/v1/objects
GET  /api/backup/v1/devices
PATCH /api/backup/v1/devices/:deviceId
```

The first three endpoints are enough for backup, restore, and conflict surfacing.

## GET `/api/backup/v1/head`

Returns all current partition heads for the authenticated user.

The client should include its last known `headSetRev` when it has one:

```text
GET /api/backup/v1/head?headSetRev=<last-known-head-set-rev>
```

The Worker first reads `backup_user_state`. If the supplied `headSetRev` still matches, it returns a no-change response without reading `backup_heads`.

Response:

```ts
type BackupHeadResponse = {
  serverTime: number;
  changed: boolean;
  headSetRev: string;
  capabilities: {
    apiVersion: 1;
    commitContentTypes: ["multipart/form-data"];
    maxObjectsPerCommit: number;
    maxCompressedBytesPerCommit: number;
    maxCompressedBytesPerObject: number;
  };
  heads: BackupHead[];
};

type BackupHead = {
  partitionKey: string;
  rev: string;
  objectId: string;
  schemaVersion: number;
  contentHash: string;
  compressedHash: string;
  compressedBytes: number;
  updatedAt: number;
  sourceDeviceId?: string;
  sourceDeviceLabel?: string;
  deletedAt?: number;
};
```

When `changed` is `false`, `heads` is empty and `headSetRev` is the still-current token. Capability values should be static Worker configuration values, not values calculated by scanning D1 or R2.

`updatedAt`, `sourceDeviceId`, and `sourceDeviceLabel` are for user conflict decisions. Hashes are for machines.

## POST `/api/backup/v1/commits`

Atomically publishes changed objects and/or deletes.

The request should use `multipart/form-data` so gzip bytes are sent as raw binary instead of base64 text.

Multipart parts:

```text
manifest: application/json
<commitObjectKey>: application/gzip
<commitObjectKey>: application/gzip
...
```

Request:

```ts
type BackupCommitRequest = {
  idempotencyKey: string;
  deviceId: string;
  deviceLabel?: string;
  puts: {
    commitObjectKey: string;
    partitionKey: string;
    schemaVersion: number;
    contentHash: string;
    compressedHash: string;
    logicalBytes?: number;
    compressedBytes: number;
    writeMode:
      | { kind: "ifMatch"; expectedRev: string }
      | { kind: "ifAbsent" }
      | { kind: "overwrite" };
  }[];
  deletes: {
    partitionKey: string;
    writeMode:
      | { kind: "ifMatch"; expectedRev: string }
      | { kind: "overwrite" };
  }[];
};
```

Write modes:

- `ifMatch`: normal safe sync; write only if the current head still has `expectedRev`.
- `ifAbsent`: first backup; write only if no current head exists.
- `overwrite`: intentional replacement; ignore the current rev.

Use `overwrite` only for explicit user actions such as "replace cloud with this import" or "use local" after a conflict. Normal background backup should use `ifMatch` or `ifAbsent`.

Server behavior:

1. Authenticate and check entitlement.
2. Resolve/register the device row.
3. Check commit `idempotencyKey`; if already committed, return the original result.
4. Validate no duplicate `partitionKey` appears in the same commit.
5. Enforce static capability limits such as max objects and max compressed bytes.
6. Read current heads for every `put` and `delete`.
7. Enforce every entry's `writeMode`.
8. If any concurrency check fails, return `409` before writing new R2 objects.
9. Validate every `commitObjectKey` has a matching gzip multipart part.
10. Verify compressed byte hashes while streaming request parts to R2 object keys.
11. Generate one new `rev` per changed partition and one new `headSetRev` for the user's head set.
12. In one D1 transaction:
    - insert `backup_commits`
    - upsert/delete `backup_heads`
    - update `backup_user_state`
    - update device timestamps

If R2 writes succeed but the final D1 transaction fails, the request may leave orphaned R2 objects. That is acceptable for V1 if object keys are server-generated, objects are not visible without D1 heads, and a later cleanup job can remove unreferenced objects.

Success response:

```ts
type BackupCommitResponse = {
  idempotencyKey: string;
  committedAt: number;
  headSetRev: string;
  heads: BackupHead[];
};
```

Conflict response:

```ts
type BackupCommitConflictResponse = {
  error: "revision_conflict";
  conflicts: {
    partitionKey: string;
    writeMode: BackupCommitRequest["puts"][number]["writeMode"];
    currentHead?: BackupHead;
  }[];
};
```

HTTP status: `409`.

## POST `/api/backup/v1/objects`

Downloads one or more immutable backup objects by id.

Request:

```ts
type BackupObjectDownloadRequest = {
  objectIds: string[];
};
```

Response should also use `multipart/form-data` when returning multiple gzip objects.

Multipart parts:

```text
manifest: application/json
<objectId>: application/gzip
<objectId>: application/gzip
...
```

Manifest:

```ts
type BackupObjectDownloadManifest = {
  objects: {
    objectId: string;
    partitionKey: string;
    rev: string;
    schemaVersion: number;
    contentHash: string;
    compressedHash: string;
    compressedBytes: number;
  }[];
};
```

If the response is too large or fails over a poor connection, the client retries with fewer `objectIds`.

## Revisions

`rev` is a per-partition opaque token generated by the server whenever a head changes.

It is not global and it is not client-incremented.

Example:

1. Device A reads `builds/all` at `rev_1`.
2. Device B reads `builds/all` at `rev_1`.
3. Device A commits with `writeMode: { kind: "ifMatch", expectedRev: "rev_1" }`.
4. Server accepts and creates `rev_2`.
5. Device B commits with `expectedRev: "rev_1"`.
6. Server rejects with `409` because current head is now `rev_2`.

This is optimistic concurrency.

## Partition Granularity

Use coarse partition keys by default in V1. The goal is to reduce D1 write volume and Worker request count before optimizing upload byte size.

Initial account split:

| Partition key shape | Contents |
| --- | --- |
| `profile.app/{profileId}` | Game profile metadata, profile-scoped app settings, freeze state, and other small profile-scoped app data. |
| `profile.game/{profileId}` | Character data plus weapon inventory. Weapon equipment is local to weapon entries. |
| `profile.artifacts/{profileId}` | Artifact inventory. Equipped character id is local to each artifact item. |

Global build data should include artifact score global settings instead of creating a separate `settings/default` partition for three numeric weights.

Other V1 partitions should remain domain-level unless measurements show a need to split them:

- `builds/all`
- `teams/all`
- `tiers/all`

Before locking the final descriptor list, evaluate current local backup payload sizes after canonical JSON and gzip compression. Only split more granularly when a partition is large enough or unreliable enough to justify extra D1 writes.

The API does not need to know why a key was split. The frontend registry and adapters own partition generation.

## Conflict Flow

Normal backup:

1. Client fetches `/head`.
2. Client builds local partitions and hashes them.
3. Client skips partitions whose `contentHash` already matches the head.
4. Client commits changed partitions with `ifMatch` or `ifAbsent` in one multipart request if possible.
5. If the request fails due to size or network reliability, client retries with fewer changed partitions.

Manual import / replace cloud:

1. Client builds affected partitions from the import.
2. Client commits changed partitions with `overwrite` only after explicit user intent.

Conflict:

1. Server returns `409` with current heads.
2. Client shows local vs cloud using `updatedAt`, source device label, and domain labels derived from `partitionKey`.
3. User chooses cloud: download current objects and apply locally.
4. User chooses local: upload if needed and commit with explicit `overwrite`, or refresh and use `ifMatch` against the displayed current rev.

## Domain-Agnostic Behavior

The Worker stores:

- partition key
- schema version
- object id
- revision
- hashes
- sizes
- timestamps
- source device row

The Worker does not parse backup payloads.

Adding a new backed-up domain should require:

1. Add a frontend adapter/registry descriptor.
2. Ensure generated `partitionKey` is stable.
3. Add tests.

No new route should be required.

## Error Codes

Recommended JSON errors:

```ts
type ApiError =
  | { error: "unauthenticated" }
  | { error: "entitlement_required"; code: "cloud_sync" }
  | { error: "payload_too_large"; maxCompressedBytes: number }
  | { error: "hash_mismatch"; field: "contentHash" | "compressedHash" }
  | { error: "revision_conflict"; conflicts: BackupCommitConflictResponse["conflicts"] }
  | { error: "object_not_found" }
  | { error: "rate_limited"; retryAfterSeconds: number };
```

Use HTTP status:

- `401` unauthenticated
- `403` entitlement or ownership failure
- `404` object not found
- `409` revision conflict
- `413` payload too large
- `422` invalid payload/hash/schema
- `429` rate limited

## Implementation Order

Recommended build order:

1. Measure current adapter payload sizes after canonical JSON and gzip compression to choose the initial coarse partition split.
2. Add D1 migration for `backup_user_state`, `backup_devices`, `backup_heads`, and `backup_commits`; add `backup_objects` only if V1 keeps explicit object history.
3. Add Worker route skeleton under `/api/backup/v1/*`.
4. Add auth middleware stub with a clear production blocker: no public backup without real `requireUser`.
5. Implement `GET /api/backup/v1/head` with the cheap `headSetRev` no-change path.
6. Implement multipart `POST /api/backup/v1/commits`.
7. Implement `POST /api/backup/v1/objects`.
8. Add frontend backup coordinator that consumes heads and calls `planCloudSync`.

Do not wire automatic triggers until the manual backup/restore path is correct.
