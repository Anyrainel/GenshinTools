# 充能需求计算系统说明

本文面向不读代码的机制审核者。目标是说明：系统需要哪些资料、如何把一条队伍循环换算成每个角色的充能需求、哪些地方是明确计算，哪些地方依赖用户按实战情况调整。

## 1. 系统要回答什么

充能计算器回答的是：

> 在这条操作轴里，每个角色为了在对应时间点开出元素爆发，至少需要多少元素充能效率？

系统输出的是“需求充能”，不是角色当前面板充能，也不是伤害。结果可以写回队伍配置的最低充能要求，供后续配装优化使用。

核心计算式是：

```text
固定回能 + (微粒/元素球回能 + 会随充能效率提高的回能) × 充能效率 / 100 >= 元素爆发消耗
```

本文会给主要数据项一个简短内部名，作用类似数学公式中的变量名，不代表代码名。变量版公式是：

```text
E_flat + (E_particle + E_scalable) × ER / 100 >= CostQ
```

也就是：

```text
需求充能 = max(100%, (爆发消耗 - 固定回能) / 可被充能放大的回能 × 100%)
```

如果固定回能已经足够开大，需求就是 100%。如果固定回能不够，又没有任何能被充能效率放大的能量来源，则该窗口无法靠堆充能解决。

## 2. 系统需要哪些资料

### 2.1 队伍配置资料

每次计算都会读取当前队伍的实际配置：

| 数据项 | 内部名 | 审核含义 |
|---|---|---|
| 队伍角色 | `Team` | 参与计算的 1-4 名角色 |
| 角色元素 | `Elem` | 角色自身元素，用于判断同元素/异元素微粒 |
| 元素爆发消耗 | `CostQ` | 该角色开大需要多少能量 |
| 命座 | `Cons` | 判断命座门槛回能是否生效 |
| 有效天赋等级 | `Talent` | 读取随天赋等级变化的回能数值 |
| 武器与精炼 | `Weapon`, `Refine` | 判断武器回能类型和数值 |
| 圣遗物套装 | `ArtifactSet` | 判断是否存在套装回能 |
| 武器类型 | `WeaponClass` | 普通攻击自然回能的概率规则与武器类型有关 |
| 治疗动作锚点 | `HealAction` | 部分“被治疗后回能”的武器需要知道治疗更接近战技还是爆发 |

这些资料来自应用内已经整理好的游戏数据、账号导入数据和用户在队伍页里的覆盖设置。

### 2.2 角色产球资料

系统保存了一份“角色产球资料表”。它描述每个角色在不同动作下会产生多少元素微粒：

| 数据项 | 内部名 | 审核含义 |
|---|---|---|
| 产球元素 | `ParticleElem` | 产生的是火、水、雷等元素微粒，还是无色微粒 |
| 点按战技产球 | `P_E` | 使用点按 E 时产生多少微粒 |
| 长按战技产球 | `P_holdE` | 使用长按 E 时产生多少微粒；没有单独资料时按点按处理 |
| 特殊战技产球 | `P_specialE` | 强化战技、特殊分支或需要单独表达的战技产球 |
| 普攻/重击/下落产球模式 | `P_attack` | 某些角色在强化普攻、重击或下落攻击中按循环规则产球 |
| 后台/周期产球 | `P_periodic` | 召唤物、领域、协同攻击等在后台多次产球 |
| 默认触发次数 | `N_periodic` | 后台产球在一轮常见循环中默认放几次，用户可以手动改 |
| 概率产球 | `P_rng` | 例如“必定 2 个，25% 概率多 1 个” |
| 未完全建模备注 | `ParticleNote` | 当前资料格式无法完全表达的机制，例如层数、状态或多动作共用冷却 |

这些最终资料主要来自三类来源：

- gcsim 的实战模拟实现：优先使用，因为它直接描述角色在模拟中何时产生微粒、概率如何、冷却如何。
- 社区 wiki 的能量资料：用于补全覆盖面，尤其是 gcsim 没覆盖或尚未同步的角色。
- 数据挖掘资料：用于交叉检查概率、事件来源和新角色资料。

最终进入计算的是一份经过合并和人工审查后的产球资料；中间来源只用于校对，不会在计算时动态切换。

### 2.3 角色自身回能和队伍回能资料

系统还保存了一份“角色回能效果资料表”，只记录会恢复标准元素能量的效果。它来自角色天赋、固有天赋和命座文本，并会对照天赋倍率表。

每条回能效果会表达这些信息：

| 数据项 | 内部名 | 审核含义 |
|---|---|---|
| 来源 | `EnergySource` | 来自哪个技能、固有天赋或命座 |
| 触发动作 | `Trigger` | 在战技、爆发、普攻、重击、下落等哪个动作上触发 |
| 回能数值 | `E_flatProc` | 每次恢复多少固定能量 |
| 百分比返还 | `RefundPct` | 按元素爆发消耗的一定比例折算成固定能量 |
| 天赋等级相关数值 | `TalentValue` | 回能数值随天赋等级变化时，按当前有效天赋等级读取 |
| 受充能效率影响的回能 | `E_scalableProc` | 例如“每 100% 充能效率恢复 X 点能量” |
| 目标 | `Target` | 给自己、全队、队友、或当前场上角色 |
| 命座要求 | `MinCons` | 需要达到几命才生效 |
| 触发次数 | `ProcCount` | 一个触发窗口内可以恢复几次 |
| 条件说明 | `Condition` | 暴击、反应、敌人数量、生命值、能量阈值等条件 |

审核时要特别注意：系统会自动判断动作、命座和目标，但不会真正模拟“是否暴击”“敌人是否满足条件”“生命值是否在阈值内”等复杂条件。这类内容会作为说明展示，需要用户按实际循环决定是否应保留或用自定义能量修正。

不属于标准元素能量池的角色专属资源不会计入，例如某些层数、特殊能量条、机制点数等。

### 2.4 武器回能资料

武器回能不是统一表格，因为每把武器的条件差异较大。系统目前按武器效果逐个实现，审核时可以按以下类别理解：

| 类别 | 内部名 | 计算逻辑 |
|---|---|---|
| 西风系列 | `W_fav` | 触发一次产生 3 个无色微粒；系统按精炼给默认触发次数，用户可逐节点开关 |
| 爆发触发固定回能 | `W_burstFlat` | 持有者释放元素爆发时获得固定能量 |
| 战技触发固定回能 | `W_skillFlat` | 持有者释放元素战技时获得固定能量 |
| 治疗相关回能 | `W_healFlat` | 持有者具备治疗能力时，在其主要治疗动作上触发 |
| 反应相关回能 | `W_reactionFlat` | 用户在对应动作上勾选“触发反应”后才计入 |
| 队伍下落攻击相关回能 | `W_partyPlungeFlat` | 队伍中有人进行下落攻击时，给武器持有者触发 |

只提供攻击、伤害、元素充能效率等属性加成的武器不在这里处理；这些属于伤害或面板计算，不是“获得能量”。

### 2.5 圣遗物回能资料

当前按套装效果单独处理：

| 套装 | 内部名 | 计算逻辑 |
|---|---|---|
| 流放者 4 件套 | `A_exile4` | 装备者释放元素爆发后，给其他队友分多次恢复固定能量 |
| 学者 4 件套 | `A_scholar4` | 由于“获得微粒后给弓/法器队友回能”的触发和冷却不易在当前用户界面中准确表达，队伍计算页面当前不计入它，并会提示结果略偏高 |

## 3. 操作轴如何表达游戏机制

系统不做帧级模拟。用户输入的是一条离散的操作轴，例如：

```text
班尼特 E -> 香菱 Q -> 香菱 E -> 行秋 E -> 行秋 Q -> 班尼特 Q
```

操作轴中可以放：

- 战技、长按战技、特殊战技。
- 元素爆发和特殊爆发。
- 普攻、重击、下落攻击。
- 等待节点，用来表示角色留场接球。
- 自定义能量节点。
- 怪物掉落元素球节点。
- 后台/周期产球节点，如奥兹、锅巴、雷神眼、岩脊共鸣等。

后台产球不是一个新的角色动作，而是“某个后台来源在这个时间点产生微粒，并由当时前台角色吸收”。用户可以拖动这些后台产球，让吸收者符合自己理解的真实循环。

## 4. 计算模式

页面上有三个关键选择。

### 4.1 初始能量：零或满

- 选择“满能量”：系统认为开始计算时每个角色都已经有足够能量开第一次大招。因此更偏向检查长期循环能否维持。
- 选择“零能量”：系统认为从 0 能量开始，需要检查启动过程能否把第一次大招充出来。

### 4.2 循环轴：只跑一次或无限重复

- “只跑一次”：只检查当前写出的这段轴。
- “无限重复”：系统会连续计算两遍循环轴。第一遍相当于当前循环，第二遍用于检查每个角色从上一轮开大后到下一轮再次开大前，能量是否还能接上。

### 4.3 启动轴和循环轴

用户可以在循环轴前添加一个或多个启动轴。启动轴用于表达开局铺场、第一轮额外充能、第一次循环和后续循环不同等情况。

结果会保留每个角色每次大招的窗口，并标出真正决定需求的“瓶颈窗口”。如果一个角色有多个大招窗口，最终需求取最难满足的那个。

## 5. 微粒和能量如何归属

### 5.1 谁接到微粒

系统用“下一个动作的角色接到上一段主动作微粒”来近似粒子飞行时间。

```text
班尼特 E -> 香菱 Q
```

当前实现中，班尼特 E 的微粒由下一个操作节点的角色香菱吸收，并且会先计入香菱这次 Q 的能量窗口，再检查香菱 Q 的消耗。也就是说，这个模型是“先吸收，再消耗”。曾考虑过另一种模型：如果下一个节点是 Q，则先消耗再吸收；但当前系统没有采用这种规则。

如果想表达班尼特自己等球，可以写成：

```text
班尼特 E -> 班尼特等待 -> 香菱 Q
```

后台产球则由用户放在哪个时间点决定：放在香菱动作上，就是香菱前台接；放在行秋动作上，就是行秋前台接。

在无限循环模式下，循环轴最后一个动作产生的微粒可以回到循环轴第一个动作的角色处吸收。

### 5.2 所有队友都会获得能量

每次微粒事件发生时，全队都会获得能量：

- 前台吸收者获得完整前台能量。
- 后台角色获得较低比例的后台能量。

后台倍率按队伍人数：

| 队伍人数 | 后台获得比例 |
|---:|---:|
| 1 | 100% |
| 2 | 80% |
| 3 | 70% |
| 4 | 60% |

### 5.3 微粒元素倍率

在 100% 充能效率下，每个微粒的基础能量是：

| 微粒关系 | 能量 |
|---|---:|
| 同元素微粒 | 3 |
| 异元素微粒 | 1 |
| 无色微粒 | 2 |

敌人掉落的元素球按 3 倍微粒计算。例如 1 个火元素球等价于 3 个火微粒。

## 6. 每个大招窗口如何计算

系统不是把整条循环的所有能量加在一起，而是按每个角色的元素爆发切窗口。

对某个角色来说：

1. 从上一次该角色开大之后开始累计能量。
2. 遇到该角色下一次开大时，检查这段窗口里累计的能量是否够。
3. 用公式反推这个窗口需要多少充能。
4. 清空该角色的累计能量，进入下一段窗口。
5. 如果有多个窗口，取需求最高的窗口作为最终结果。

窗口内的能量分三类：

| 类别 | 内部名 | 是否受充能效率影响 | 例子 |
|---|---|---|---|
| 微粒/元素球回能 | `E_particle` | 是 | 角色战技产球、后台产球、西风微粒、怪物掉球 |
| 可充能固定回能 | `E_scalable` | 是 | 文本明确写“每 100% 元素充能效率恢复 X 点”的效果 |
| 固定回能 | `E_flat` | 否 | 试作金珀、流放者、琴的爆发返还、用户手动固定赋能 |

## 7. 自动优化充能做了什么

“自动优化充能”不是完整的队伍循环生成器，也不会判断最优实战手法。它只是尝试对已有操作轴做少量安全编辑，让接球更合理、需求更低。

它会尝试：

- 在产球动作后插入等待，让产球者自己接球。
- 在产球动作后、下一个角色开大前插入等待，让下一个角色提前上场接球。
- 删除已经存在但导致结果更差的等待。
- 对同一角色相邻的“产球动作”和“大招”尝试交换顺序。

评价方式是先降低队伍中最高的充能需求；最高需求相同，再看第二高、第三高。它最多迭代 20 次，找不到更好的改动就停止。

它不会：

- 自动增加新的战技次数。
- 自动改变后台产球次数。
- 自动判断西风是否真的暴击。
- 自动判断反应武器的条件是否满足。
- 保证找到全局最优循环。

## 8. 用户可以如何模拟更真实的情况

为了弥补事件模型不做帧级模拟的限制，系统提供了这些高级调节：

| 选项 | 用途 |
|---|---|
| 启动轴 | 表达第一轮和后续循环不同 |
| 循环轴重复 | 检查长期循环，而不是只看第一轮 |
| 最低/期望/最高产球 | 选择按保守、平均或理想概率计算 |
| 等待节点 | 手动控制谁吃上一段微粒 |
| 后台产球拖动 | 手动指定召唤物/协同攻击的微粒由谁吸收 |
| 西风开关 | 逐节点决定是否触发西风 |
| 反应开关 | 逐节点决定是否满足反应武器或双雷共鸣条件 |
| 怪物产球 | 手动添加破盾、击杀等敌方掉落元素球 |
| 自定义能量 | 补充系统未建模的固定回能，或按爆发消耗百分比折算固定回能 |

## 9. 当前主要假设和限制

审核时应默认以下近似存在：

- 不模拟真实时间、帧数、粒子飞行时间和大招扣能延迟。
- 不自动判断敌人数量、敌人状态、生命值阈值、暴击、反应类型等条件。
- 后台产球默认次数只是常见循环估算，需要按具体循环调整。
- 冷却时间大多作为资料备注，不是通用的时间轴约束。
- 某些“随充能效率恢复能量”的上限目前没有精确求解，只按每 100% 的线性值计入。
- 特殊爆发动作目前仍按角色的同一个爆发消耗处理。
- 学者 4 件套当前在队伍计算页面的充能结果中不计入。
- 敌人掉球必须由用户手动添加。

## 10. 审核建议

建议按以下顺序检查：

1. 这条操作轴是否符合真实手法，尤其是每个角色何时开大。
2. 关键产球动作的微粒数量和概率是否合理。
3. 后台产球次数是否符合这条循环的持续时间和触发频率。
4. 每段关键微粒由谁接到是否合理；如果不合理，应调整等待或后台产球位置。
5. 西风、反应武器、暴击回能、生命值条件、敌人数量条件是否真的满足。
6. 怪物掉球是否需要手动加入。
7. 最终瓶颈窗口是否符合直觉；如果不符合，优先检查该窗口之前的接球和回能条件。

## 11. 简洁例子

假设某角色元素爆发消耗 60。一个窗口内，它前台吃到 4 个同元素微粒，又获得 15 点固定回能。

同元素微粒前台每个给 3 点 100% 充能下的能量：

```text
微粒回能 = 4 × 3 = 12
固定回能 = 15
爆发消耗 = 60
```

需求为：

```text
(60 - 15) / 12 × 100% = 375%
```

如果同一个窗口额外吃到 2 个无色微粒，无色微粒每个给 2 点：

```text
可被充能放大的回能 = 12 + 2 × 2 = 16
需求 = (60 - 15) / 16 × 100% = 281.25%
```

界面会向上显示约 282%。这个例子体现了系统最核心的审核思路：先确认窗口、再确认能量归属、再确认哪些能量吃充能，最后反推需求。
