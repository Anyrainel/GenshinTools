# Account System Design 3: D1, R2, and Payload Schema Draft

Last updated: 2026-04-30.

## Scope

This document drafts the backend schema for auth, entitlements, cloud sync, lightweight analytics, feedback, and first-party ad sponsorships.

The design assumes:

- D1 stores transactional metadata.
- R2 stores compressed backup objects.
- Local app stores keep their existing migration/hydration responsibilities.
- Cloud payloads have independent namespace versions.

## Naming Rules

- Use `TEXT` ids generated by the server. UUID v7 or ULID are both fine.
- Store timestamps as Unix milliseconds in `INTEGER`.
- Store immutable provider events before mutating entitlement state.
- Store backup objects in R2 and only references/hashes in D1.
- Avoid raw analytics events unless debugging a short-lived incident.

## Core Auth Tables

```sql
CREATE TABLE users (
  id TEXT PRIMARY KEY,
  created_at INTEGER NOT NULL,
  updated_at INTEGER NOT NULL,
  display_name TEXT,
  primary_email TEXT,
  locale TEXT,
  region_hint TEXT,
  role TEXT NOT NULL DEFAULT 'user',
  disabled_at INTEGER
);

CREATE TABLE user_identities (
  id TEXT PRIMARY KEY,
  user_id TEXT NOT NULL REFERENCES users(id) ON DELETE CASCADE,
  provider TEXT NOT NULL,
  provider_subject TEXT NOT NULL,
  email TEXT,
  email_verified INTEGER NOT NULL DEFAULT 0,
  display_name TEXT,
  avatar_url TEXT,
  linked_at INTEGER NOT NULL,
  last_login_at INTEGER,
  UNIQUE(provider, provider_subject)
);

CREATE INDEX idx_user_identities_user
  ON user_identities(user_id);

CREATE TABLE sessions (
  id TEXT PRIMARY KEY,
  user_id TEXT NOT NULL REFERENCES users(id) ON DELETE CASCADE,
  session_hash TEXT NOT NULL UNIQUE,
  created_at INTEGER NOT NULL,
  last_seen_at INTEGER NOT NULL,
  expires_at INTEGER NOT NULL,
  revoked_at INTEGER,
  user_agent_hash TEXT,
  ip_hash TEXT,
  device_label TEXT
);

CREATE INDEX idx_sessions_user
  ON sessions(user_id, expires_at);
```

`session_hash` is a hash of the opaque cookie token, not the token itself.

`sessions` are first-party app sessions after SSO login. They let us expire sessions, revoke one device, support "log out all devices", show device labels, and avoid re-running provider OAuth on every API call. Store only the hash of the opaque cookie token.

For OAuth/OIDC identities:

- `user_identities.provider` is the provider code, such as `google`, `github`, `gitee`, or `wechat`.
- `user_identities.provider_subject` is the stable provider subject/user id after provider response validation.
- Provider client secrets, private keys, webhook signing secrets, token-encryption keys, and client-secret rotation metadata live in Cloudflare Workers secrets or Secrets Store, not D1.
- V1 provider metadata should be static Worker/server config: provider code, issuer URL, auth URL, token URL, JWKS URL, client id, scopes, and redirect path. Do not add a D1 provider-config table until runtime admin changes are needed.
- OAuth callback transaction state should stay local in short-lived HTTP-only, Secure, SameSite=Lax cookies: `state`, OIDC `nonce`, PKCE `code_verifier`, and optional post-login redirect. Add a D1 login-state table later only if cookies become insufficient.
- Use Authorization Code flow. Do not use implicit flow or resource owner password credentials grant.
- Use PKCE `S256` when the provider supports it.
- Validate `state` on every callback and validate OIDC `nonce` before accepting issued tokens.
- Validate OIDC issuer, audience/client id, authorized party when present, signature/JWKS or provider-specific token validation, expiry, and UserInfo `sub` equality.
- Do not store provider access tokens or refresh tokens in V1. If a later feature requires them, encrypt tokens with a key from Workers secrets, minimize scopes, and keep short retention.
- Do not log raw auth codes, provider tokens, client secrets, raw `state`, raw `nonce`, or raw `code_verifier`.

## Email and Password Auth V2 Schema

Email/password is not part of V1. Do not create these tables or endpoints in the initial migration unless we explicitly choose Workers Paid or a managed auth provider.

If V2 adds email/password, reserve provider code `email_password` and add:

```sql
CREATE TABLE password_credentials (
  identity_id TEXT PRIMARY KEY REFERENCES user_identities(id) ON DELETE CASCADE,
  password_hash_phc TEXT NOT NULL,
  password_hash_version INTEGER NOT NULL,
  pepper_version INTEGER,
  password_updated_at INTEGER NOT NULL,
  password_reset_required_at INTEGER,
  last_verified_at INTEGER
);

CREATE TABLE auth_challenges (
  id TEXT PRIMARY KEY,
  user_id TEXT REFERENCES users(id) ON DELETE CASCADE,
  identity_id TEXT REFERENCES user_identities(id) ON DELETE CASCADE,
  purpose TEXT NOT NULL,
  destination_hash TEXT NOT NULL,
  token_hash TEXT NOT NULL UNIQUE,
  created_at INTEGER NOT NULL,
  expires_at INTEGER NOT NULL,
  consumed_at INTEGER,
  attempt_count INTEGER NOT NULL DEFAULT 0
);

CREATE INDEX idx_auth_challenges_identity
  ON auth_challenges(identity_id, purpose, expires_at);

CREATE TABLE auth_rate_limits (
  scope TEXT NOT NULL,
  key_hash TEXT NOT NULL,
  window_start_at INTEGER NOT NULL,
  attempt_count INTEGER NOT NULL,
  locked_until INTEGER,
  updated_at INTEGER NOT NULL,
  PRIMARY KEY(scope, key_hash)
);
```

For email/password identities:

- `user_identities.provider = 'email_password'`.
- `user_identities.provider_subject` is the normalized email address.
- `password_credentials.password_hash_phc` stores an Argon2id PHC string or equivalent library-native encoded verifier, never plaintext or reversible encryption.
- The password pepper is stored only in Cloudflare Workers secrets. D1 stores at most `pepper_version`.
- `password_hash_version` tracks the current application policy so successful login can rehash older credentials.
- `auth_challenges` stores hashed email-verification and password-reset tokens only. Tokens are short-lived and single-use.
- `auth_rate_limits` stores coarse counters for login, signup, email verification, and password reset flows. Use normalized-email and IP/coarse-network keys; store hashes of those keys.

Password implementation requirements:

- Use Argon2id with per-password salts. Start from OWASP's current Argon2id baseline, then tune in the actual Worker runtime.
- If Argon2id cannot run with an acceptable budget in Workers, use a vetted managed auth provider or separate auth service rather than using a fast hash.
- Accept at least 64-character passwords, allow spaces and Unicode, NFC-normalize before hashing, and never silently truncate.
- Require 15 characters while password is the only factor. Do not impose character-composition rules.
- Block common, expected, service-specific, and known-compromised passwords when creating or changing passwords.
- Do not use security questions or password hints.
- Do not log raw passwords, raw tokens, or raw session ids.
- Return generic errors for login and reset requests to avoid account enumeration.

## Cloud Sync Tables

Cloud sync stores versioned objects by namespace and partition.

```sql
CREATE TABLE sync_objects (
  id TEXT PRIMARY KEY,
  user_id TEXT NOT NULL REFERENCES users(id) ON DELETE CASCADE,
  namespace TEXT NOT NULL,
  partition_key TEXT NOT NULL,
  rev TEXT NOT NULL,
  base_rev TEXT,
  schema_version INTEGER NOT NULL,
  r2_key TEXT NOT NULL,
  content_hash TEXT NOT NULL,
  compressed_hash TEXT,
  compression TEXT NOT NULL,
  media_type TEXT NOT NULL,
  logical_bytes INTEGER NOT NULL,
  compressed_bytes INTEGER NOT NULL,
  source_device_id TEXT REFERENCES sync_devices(id) ON DELETE SET NULL,
  created_at INTEGER NOT NULL,
  superseded_at INTEGER,
  deleted_at INTEGER,
  UNIQUE(user_id, namespace, partition_key, rev)
);

CREATE INDEX idx_sync_objects_user_ns
  ON sync_objects(user_id, namespace, partition_key, created_at);

CREATE TABLE sync_heads (
  user_id TEXT NOT NULL REFERENCES users(id) ON DELETE CASCADE,
  namespace TEXT NOT NULL,
  partition_key TEXT NOT NULL,
  object_id TEXT NOT NULL REFERENCES sync_objects(id) ON DELETE CASCADE,
  rev TEXT NOT NULL,
  updated_at INTEGER NOT NULL,
  soft_deleted_at INTEGER,
  PRIMARY KEY(user_id, namespace, partition_key)
);
```

`sync_heads` plus `sync_objects` are the source of truth for the current cloud index. Do not add a stored manifest table in V1.

In this design, "cloud index" means the response from `GET /api/sync/index`: a compact list of current cloud heads by namespace/partition. It is an index the client reads before upload or restore, not a separate persisted document. The server composes it from `sync_heads` joined to `sync_objects`.

Suggested namespaces:

| Account | `account.weapons` | account profile id | normalized non-disposable weapons | Latest complete import for that profile can overwrite |

| Builds | `builds` | `default` | artifact build deltas | Explicit local/cloud choice |

## R2 Object Keys

Use deterministic path segments but not public URLs:

```text
users/{user_id}/sync/{namespace}/{partition_key}/{rev}.json.gz
```

`namespace`, `partition_key`, and `rev` must be encoded as path-safe segments before building the key. Use a simple allowlist for generated ids where possible, and otherwise use URL-safe base64/base64url encoding. Never let raw user-controlled text become an R2 path segment.

Example:

```text
users/usr_01HX/sync/account.artifacts/uid-600000000/rev_01JZ.json.gz
```

R2 object metadata:

```text
content-type: application/json
content-encoding: gzip
x-genshin-tools-namespace: account.artifacts
x-genshin-tools-schema-version: 1
x-genshin-tools-content-hash: sha256:...
x-genshin-tools-compressed-hash: sha256:...
```

## Cloud Payload Envelope

Every R2 object stores a JSON envelope before compression:

```ts
type CloudPayloadEnvelope<T> = {
  app: "GenshinTools";
  schemaVersion: number;
  namespace: string;
  partitionKey: string;
  rev: string;
  baseRev?: string;
  createdAt: number;
  sourceDeviceId?: string;
  contentHash: string;
  payload: T;
};
```

`contentHash` is the hash of canonical JSON for `payload`, not the compressed bytes.

Type names in the main code should represent the latest shape and should not carry suffixes like `V1`. The payload envelope's `schemaVersion` is the wire-version source of truth. Historical shapes should live in migration modules and may use versioned names there, for example `AccountArtifactsPayloadV1Schema`.

## Account Payloads

### `account.profile`

```ts
type AccountProfileId = number; // 0 for default/no UID, otherwise numeric UID

type AccountProfilePayload = {
  accountProfileId: AccountProfileId;
  name: string;
  /** Missing for the default/no-UID profile. Never display accountProfileId 0 as a UID. */
  uid?: number;
  region?: "global" | "cn" | string;
  lastImportedAt?: number;
  source?: "good" | "enka" | "hoyolab" | "manual" | "scanner" | string;
  softDeletedAt?: number;
};
```

Profile `0` is a real profile key, not a game UID. Local imports already rename account-scoped stores before activating a promoted UID. Cloud sync should mirror that behavior by moving account-scoped partitions from `0` to the UID and marking the old `0` heads as soft-deleted. Importing the same UID again should reactivate/overwrite soft-deleted data for that UID.

### `account.characters`

```ts
type AccountCharactersPayload = {

    constellation: number;

```

Equipment is intentionally not stored here. Use `account.equipment` as the single source of truth for equipped item links so equip changes do not rewrite both character state and item inventory partitions.

### `account.weapons`

```ts
type AccountWeaponsPayload = {
  accountProfileId: AccountProfileId;
  weapons: {
    id: string;
    identity?: {
      fingerprint: string;
      occurrence: number;
      sourceInstanceId?: string;
    };
    key: string;
    rarity: number;
    level: number;
    refinement: number;
    lock: boolean;
  }[];
};
```

Cloud backup intentionally excludes disposable weapons:

```ts
function shouldSkipWeaponForCloud(weapon: {
  rarity: number;
  level: number;
  refinement: number;
  lock: boolean;
  equippedCharId?: string;
}) {
  return (
    !weapon.lock &&
    weapon.rarity === 3 &&
    weapon.level === 1 &&
    weapon.refinement === 1 &&
    !weapon.equippedCharId
  );
}
```

The filter runs at the cloud codec boundary. Local stores may keep skipped weapons. Restore does not recreate skipped disposable weapons.

### `account.artifacts`

```ts
type AccountArtifactsPayload = {
  accountProfileId: AccountProfileId;
  setGroup: string;
  artifacts: {
    id: string;
    identity?: {
      fingerprint: string;
      occurrence: number;
      sourceInstanceId?: string;
    };
    setKey: string;
    slotKey: "flower" | "plume" | "sands" | "goblet" | "circlet";
    level: number;
    rarity: number;
    mainStatKey: string;
    lock: boolean;
    substats: Record<string, number>;
    totalRolls?: number;
    astralMark?: boolean;
    elixirCrafted?: boolean;
    unactivatedSubstats?: Record<string, number>;
    initialValues?: Record<string, number>;
  }[];
};
```

`setGroup` is a stable implementation-defined artifact-set shard. It can be derived from artifact domain/source grouping, release era, or another frozen mapping, but the cloud contract only requires that the same `setKey` maps to the same `setGroup` for a given schema version.

Partition key:

```ts
`${accountProfileId}:${setGroup}`
```

Rules:

- Store a full snapshot for one set group per object.
- Do not store item-level artifact patches in V1.
- Full imports recompute every setGroup hash and upload only changed groups.
- Single artifact edits upload only that artifact's setGroup.
- If the mapping changes for existing sets, bump the artifact payload schema or run a migration that writes new shard heads and soft-deletes/supersedes old ones.

### `account.equipment`

```ts
type ArtifactSlot = "flower" | "plume" | "sands" | "goblet" | "circlet";

type AccountEquipmentPayload = {
  accountProfileId: AccountProfileId;
  equipment: {
    charId: string;
    weaponId?: string;
    artifactIds?: Partial<Record<ArtifactSlot, string>>;
  }[];
};
```

`weaponId` and `artifactIds` are account-scoped stable ids. They must not be derived from array order in the weapons/artifacts partitions.

The app can derive item-to-character indexes after hydration. Do not duplicate `equippedCharId` on every artifact/weapon row in the cloud payload, because equip changes are common and `account.artifacts` is the largest partition.

### Artifact Payload Compression

Start with normal JSON plus gzip for `account.artifacts`. Repeated object keys, stat keys, slot keys, and set keys should compress well, and this keeps V1 easy to inspect and migrate.

Before adding a custom compact codec, measure real dumps:

- logical JSON bytes for `account.artifacts`
- gzip bytes for `account.artifacts`
- upload time on slow network simulation
- Worker memory and CPU during upload/restore

Add a compact artifact codec only if gzip payloads are still too large. The preferred compact codec is dictionary/array JSON, not a bespoke binary format:

- top-level dictionaries for stat keys, set keys, slot keys, and optional source strings
- artifact rows as arrays with fixed field order
- omit default `false` and empty optional fields
- keep equipment links in `account.equipment`, not artifact rows

Later compact schema versions can replace repeated string fields with dictionaries and arrays without changing local `AccountData`.

Identity rules:

- equipped character is not part of item identity.
- `lock` is not part of item identity.
- Exact duplicate items use an occurrence suffix because the upstream sources do not always expose true unique item ids.
- Import code should preserve existing ids by matching incoming items against previous account data before assigning ids to new items.
- Exact duplicate artifacts are handled as a multiset. If two source items are fully indistinguishable, their ids are stable handles inside GenshinTools, not proof of physical-copy identity.

## Generic Preset Overlay Payload

```ts
type PresetDelta<TItem> =
  | {
      kind: "preset";
      id: string;
      displayIndex?: number;
      deleted?: true;
    }
  | {
      kind: "custom";
      id: string;
      displayIndex?: number;
      value: TItem;
    };
```

Resolver rules:

- Preset removal only comes from `deleted`.
- Preset object content comes from the preset and is immutable.
- Custom object content comes from `value`.
- Custom edits replace the full `value` in place while preserving the custom id.
- Ordering only comes from `displayIndex`.
- Missing `displayIndex` means resolver default order; it never means removal.
- Grouping is derived by resolver code, not stored by the generic item delta.
- Preset deltas cannot carry `value`; custom deltas cannot carry `deleted`.
- Duplicate `displayIndex` values are allowed. The resolver determines the group being sorted.
- If a preset item is edited, resolve it as remove preset plus create custom.
- If a custom item's id would change, resolve it as remove old custom plus create new custom and remap any external references in the same transaction.
- The persisted array should be normalized to at most one entry per `(kind, id)` before saving.

## Freeze Payload

```ts
type FrozenLoadoutCloudEntry = {
  /** Present for current team-bound freezes; optional for future global character freezes. */
  teamId?: string;
  charId: string;
  artifactIds: Partial<
    Record<"flower" | "plume" | "sands" | "goblet" | "circlet", string>
  >;
  updatedAt?: number;
};

type FreezeCloudPayload = {
  accountProfileId: AccountProfileId;
  reuseMode: "none" | "sameChar" | "forceReuse";
  standaloneArtifactIds: string[];
  loadouts: FrozenLoadoutCloudEntry[];
};
```

Normalize freeze payloads before save and after restore:

- Resolve against the matching account profile's artifact ids.
- Drop loadouts with no valid artifact ids.
- Collapse duplicate `(teamId, charId)` entries deterministically.
- Keep multiple loadouts for the same `charId` across different teams.
- Resolve `forceReuse` per target team by selecting at most one matching loadout per `charId`; do not make the cloud payload itself depend on a specific target team.

## Tier and Account Settings Payloads

Character tier lists can be linked to account profiles or unattached:

```ts
type CharacterTierListPayload = {
  /** Path-safe cloud list id; may be encoded from a local numeric id. */
  id: string;
  linkedAccountProfileId?: AccountProfileId | null;
  title?: string;
  author?: string;
  description?: string;
  tierAssignments: unknown;
  tierCustomization: unknown;
};
```

Partition rules:

- `tier.character.account/{profileId}` stores the list linked to one account profile. `linkedAccountProfileId` is a number in the payload/local store, not a formatted string.
- `tier.character.custom/{listId}` stores an unattached custom list.
- On restore, if multiple lists claim the same `linkedAccountProfileId`, keep the newest account-linked partition and import the rest as unattached lists.
- `listId` should be stable at the cloud boundary. Current local tier-list ids are numeric, so the codec can encode them as path-safe strings without changing the local store shape.
- `tier.weapon/{listId}` and `tier.artifact/{listId}` use the same stable list-id pattern and do not need account-profile linking.

Account-data workflow settings should move to account-scoped cloud namespaces:

```ts
type AccountTriagePayload = {
  accountProfileId: AccountProfileId;
  settings: unknown;
};

type AccountResourcesPayload = {
  accountProfileId: AccountProfileId;
  thresholds: unknown;
  minScoreDiff: unknown;
  visibleKinds?: {
    craft?: boolean;
    reroll?: boolean;
    levelup?: boolean;
  };
};
```

The local stores already persist settings by account profile id, so the cloud codec does not need to guess which profile owns singleton settings.

## Activity Rollup Tables

Client batches are lossy. The backend writes rollups. This is not implemented today; these tables are the proposed first-party telemetry target.

`activity_daily` is a storage granularity, not an upload schedule. The client should flush small rollup batches on idle/interval, on `visibilitychange` via `sendBeacon`, and after meaningful feature actions. The server groups accepted counters into daily rows by day.

```sql
CREATE TABLE activity_daily (
  day TEXT NOT NULL,
  event_name TEXT NOT NULL,
  route TEXT,
  locale TEXT,
  region_hint TEXT,
  app_version TEXT,
  count INTEGER NOT NULL DEFAULT 0,
  user_count_estimate INTEGER,
  updated_at INTEGER NOT NULL,
  PRIMARY KEY(day, event_name, route, locale, region_hint, app_version)
);

CREATE TABLE activity_ingest_guard (
  batch_id TEXT PRIMARY KEY,
  user_id TEXT,
  received_at INTEGER NOT NULL
);
```

Event batch request:

```ts
type ActivityBatchPayload = {
  batchId: string;
  deviceId: string;
  sentAt: number;
  appVersion: string;
  locale: string;
  events: {
    name: string;
    route?: string;
    at: number;
    sampleRate?: number;
    props?: Record<string, string | number | boolean | null>;
  }[];
};
```

For limited server resources, prefer sending pre-aggregated counters rather than raw click streams:

```ts
type ActivityRollupBatchPayload = {
  batchId: string;
  deviceId: string;
  sentAt: number;
  appVersion: string;
  locale: string;
  rollups: {
    day: string;
    eventName: string;
    route?: string;
    regionHint?: string;
    count: number;
    sampleRate?: number;
  }[];
};
```

Allowed properties must be whitelisted per event name. Do not send artifact stats, inventory contents, team names, free text, cookies, provider ids, or payment data.

If Workers Analytics Engine is enabled later, one batched request should emit one or a small number of data points, not one data point per UI click.

Do not wait until the next backup to upload activity. That would bias telemetry toward signed-in users who use backup and delay product signals. Instead, keep a small TTL-limited offline queue and drop stale counters.

## Sync Upload Contract

Request:

```ts
type SyncObjectUploadRequest = {
  namespace: string;
  partitionKey: string;
  baseRev?: string;
  schemaVersion: number;
  compression: "gzip";
  mediaType: "application/json";
  logicalBytes: number;
  compressedBytes: number;
  /** Hash of canonical JSON payload before compression. */
  contentHash: string;
  /** Optional hash of the exact compressed bytes. */
  compressedHash?: string;
};
```

Do not base64-encode backup bodies in the normal path. Base64 would inflate the largest account uploads and force extra JS/Worker memory copies.

Wire format:

- V1 uploads one partition object per request.
- The request body is the compressed bytes; metadata is JSON in a `metadata` form field or compact headers if it fits safely.
- The JSON metadata contains the `SyncObjectUploadRequest` fields above except the body bytes.
- Keep a debug-only base64 JSON path possible for tests or admin tools, not for production backup.

Response:

```ts
type SyncObjectUploadResult = {
  namespace: string;
  partitionKey: string;
  objectId: string;
  rev: string;
  accepted: true;
  conflict?: {
    currentRev: string;
    currentObjectId: string;
  };
};
```

The V1 endpoint should accept one object. Batching can be added later if request count becomes a real bottleneck.

If `baseRev` does not match the current `sync_heads` revision, return HTTP 409 with current head metadata. The client should mark that partition as paused/conflicted.

## Sync Consistency Pattern

Use D1 metadata as the source of truth and R2 as immutable blob storage.

Normal sync should not download full R2 objects just to compare local and cloud. It also should not normally issue R2 `HEAD` requests, because D1 already stores the metadata needed for comparison. R2 `HeadObject` and `GetObject` are both Class B operations; `HEAD` avoids body transfer and Worker memory pressure, but it does not avoid the read operation class. The cloud index endpoint should return, for each namespace/partition:

- current `rev`
- `objectId`
- `schemaVersion`
- `contentHash`
- `logicalBytes`
- `compressedBytes`
- `updatedAt`
- source device display metadata

Client upload flow:

1. Read the latest cloud index/head metadata near the start of a sync attempt, not from R2.
2. Convert local state through the cloud codec.
3. Canonicalize JSON and compute `contentHash`.
4. If the cloud index already has the same `contentHash` for that namespace/partition, mark the partition clean and update local sync metadata.
5. If the cloud head differs from local `lastSeenRev` and local content also differs from cloud, apply the namespace conflict policy. Global settings can latest-write, a complete account import can intentionally replace that account profile's cloud partitions, and hand-authored builds/teams/account-freeze should pause this partition as a conflict instead of uploading in the background.
6. Compress the payload.
7. Upload each dirty partition separately with local `lastSeenRev` as `baseRev`.

Server upload flow:

1. Authenticate and check `cloud_sync` entitlement for writes.
2. Validate namespace, partition, schema version, byte sizes, and hashes.
3. Read the current D1 head for `(user_id, namespace, partition_key)`.
4. If `baseRev` differs from the current head, return HTTP 409 with current head metadata.
5. Write the compressed body to R2 under an immutable key that contains the new `rev`.
6. Insert a `sync_objects` row.
7. Update `sync_heads` with a conditional SQL statement, for example `WHERE rev = ?`, or insert when no head exists.
8. If the conditional head update loses a race, return HTTP 409 and schedule orphan R2 cleanup.

Do not use R2 object overwrite semantics for sync heads. R2 conditional writes and ETags are useful for object integrity and idempotency, but D1 `sync_heads` should remain the concurrency boundary.

`contentHash` is the required logical integrity and dedupe field. `compressedHash` is optional: keep it only if we want the server to validate exact compressed bytes without decompressing, or if we want an extra transport/storage diagnostic. It is not needed for conflict control.

`baseRev` is not stored inside every Zustand store. It belongs to local sync metadata, keyed by namespace and partition, for example:

```ts
type LocalSyncMeta = {
  byPartition: Record<string, {
    lastSeenRev?: string;
    lastSeenContentHash?: string;
    lastLocalContentHash?: string;
    dirtySince?: number;
    nextAttemptAt?: number;
    attemptCount?: number;
    conflictRev?: string;
    lastError?: string;
    lastSyncedAt?: number;
  }>;
};
```

The upload client reads local app stores, converts them through codecs, and attaches the current `lastSeenRev` as `baseRev`. Successful upload or restore updates `LocalSyncMeta`. Store actions do not need to understand cloud revisions.

Read cloud head metadata at these moments:

- On login and app start, to populate sync status.
- When the tab becomes visible after a meaningful delay.
- Immediately before a background or manual upload flush.
- Before restore/download UI is shown.

Do not treat "read cloud index" as permission to overwrite. Permission to advance the cloud head comes only from the server accepting `baseRev`.

Same-browser coordination:

- Same-browser concurrent editing is not a primary design concern.
- Use a lightweight localStorage or `BroadcastChannel` signal to avoid duplicate background flushes.
- Avoid a complex leader-election system in v1.
- Use storage or broadcast events to refresh sync status in other tabs after successful upload/restore.

Restore flow:

1. Read cloud index metadata.
2. Let the client compare local `contentHash`/`baseRev` with cloud head metadata.
3. Download only selected R2 objects.
4. If present, verify `compressedHash`; decompress, then verify `contentHash`.
5. Run payload-schema migration and local store hydration/import code.

Conflict policy for the first release:

- No automatic cross-device merge.
- Do not show a modal for passive conflict detection. Show a non-blocking sync status under the account icon dropdown, such as "Cloud has newer data; local changes not uploaded."
- Ask the user only when they click sync/restore, switch device data intentionally, or attempt an action that would overwrite one side.
- If cloud head changed since local `baseRev` for hand-authored domains, offer "keep local and overwrite cloud" versus "use cloud and replace local". Keep the old local payload until the user chooses.
- For complete account imports, allow an explicit latest-import-wins path that overwrites older cloud account partitions.
- UID imports can keep the current local merge behavior. The cloud upload stores the resulting full account profile snapshot; do not implement server-side account merging in V1.
- For settings, latest-writer-wins is acceptable.
- Keep only the latest visible head per namespace/partition in V1. Mark older objects `superseded_at` and garbage collect their R2 blobs after the upload is committed. The schema keeps timestamps so a later `+N days` retention feature can be added without reshaping tables.

## Migration Strategy

There are three independent version layers:

1. D1 schema migrations: backend table shape.
2. Cloud payload namespace schema versions: `account.artifacts` schema 1, `team.config` schema 1, etc.
3. Local Zustand store versions: existing local hydration and old user migration.

Rules:

- Do not bump local store versions for cloud-only payload changes.
- Do not make cloud payloads depend on local `partialize` output directly.
- Every cloud codec needs round-trip tests.
- Restores should enter through store import/hydration paths that already repair and migrate local shapes.

## Data Deletion

Required user deletion behavior:

- Delete sessions.
- Delete identities.
- Delete OAuth login state rows associated with the user if any are still outstanding.
- If V2 email/password auth exists, delete password credentials, outstanding auth challenges, and linkable auth rate-limit rows.
- Delete sync metadata and R2 objects.
- Delete feedback or anonymize feedback depending on retention policy.
- Keep payment events if legally/accounting required, but detach from public profile where possible.
- Revoke entitlements.

Use a tombstone or audit entry if we need to prove deletion occurred without keeping the full user record.

Account-profile deletion is softer than user-account deletion:

- Mark account profile heads as `soft_deleted_at` so the profile disappears from restore/UI.
- Keep underlying latest objects for analytics/recovery unless the user requests full account deletion.
- Re-importing the same UID should reactivate that UID's soft-deleted profile by writing new heads.
- Promoting profile `0` to a UID should move account-scoped heads to the UID and soft-delete the `0` heads.
